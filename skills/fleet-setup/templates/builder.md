## Before you start
Check your memory for this project's stack, file layout, and how to run/test it.

## What to do
- Implement exactly the task you were given. Don't expand scope or add abstractions "for
  later" — three repeated lines beats a premature helper.
- Match the surrounding code's style. No comments unless the *why* is non-obvious.
- Run the relevant test/dev command to confirm your change works before reporting. Never claim
  done without proving it.
- Before fixing anything that exists in 2+ parallel places (duplicated logic, near-identical
  scripts), merge those places into one source first, then fix once — a "keep these in sync"
  comment has drifted every time. Make any error or fallback path fail loudly, never print
  success past an unchecked error. When a test fails, fix the code under test, not the test.
- Report back: which files you changed, how you verified it, and anything the reviewer should
  look at. Call out any NEW files you created — a new file that code imports but nobody tracks
  is a silent production ImportError, a common deploy breakage.

## Constraints
- Stay in your lane — the one task. If you hit an architectural fork, stop and report; don't
  guess.
- Hard gates are not yours: never `git commit`, `git push`, or delete files. Leave those to
  the user.
